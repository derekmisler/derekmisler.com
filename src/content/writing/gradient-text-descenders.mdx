The `background-clip: text` trick is one of those CSS techniques that looks great in the demo and then breaks in production. Apply a gradient, everything looks fine. Ship it, and a week later someone screenshots a heading where the bottom of every `g` and `p` has been surgically removed.

This site uses gradient text in the header and a few section labels. Getting descenders to render correctly took a few minutes of actually understanding what the browser is doing, rather than cargo-culting a Stack Overflow snippet. Here is what I found.

## The problem: what gets clipped and why

`background-clip: text` tells the browser to use the text content as a clipping mask for the element's background. Anywhere there's a glyph, the background shows through. Anywhere there isn't, it doesn't.

The clip boundary is the element's **box**, not the visible ink of the glyphs. And for an `inline-block` element (which `background-clip: text` requires), that box has a specific geometry: its bottom edge sits at the **baseline** of the text, not at the bottom of the descenders.

Descenders are the parts of letterforms that drop below the baseline: `g`, `j`, `p`, `q`, `y`, and in some fonts `f` and `z`. They extend below the baseline by a distance defined in the font's metrics as the **descender depth**, measured in UPM (units per em). IBM Plex Sans, the font used on this site, has a descender depth of roughly 0.22 UPM.

At `line-height: 1.1` (the heading line height used here), there is no extra space below the baseline to accommodate those descenders. The box bottom is exactly at the baseline. Descenders extend below it, outside the clip region, and get cut off.

## The mechanism: how the box model creates this

To understand the fix, it helps to understand exactly why the box ends where it does.

When you write:

```css
.gradient-text {
  display: inline-block;
  color: transparent;
  background-clip: text;
}
```

The browser constructs a **line box** for the element. The line box height is derived from the font metrics: specifically from the **ascender** and **cap height** above the baseline. The descender depth is not included in the box height calculation unless extra space is provided through `line-height`, `padding`, or `margin`.

With `line-height: 1.1` on a font where the combined ascender + descender exceeds 1.1em (as it does for IBM Plex Sans), the box is too short to contain the full glyph extent. The background region gets clipped to the box, and the descenders are below it.

This is not a bug. It is the box model working as specified. The fix is to extend the box to cover the descenders, which means extending it downward.

## The fix: padding-bottom + margin-bottom

Two CSS properties, one line each:

```css
.gradient-text {
  @supports (background-clip: text) {
    display: inline-block;
    color: transparent;
    background-image: linear-gradient(135deg, var(--color-text), var(--color-accent));
    background-clip: text;

    /* Extend the clip region below the baseline to cover descenders.
       0.2em gives ~0.22em of clearance at any font size. */
    padding-bottom: 0.2em;

    /* Undo the layout displacement the padding would otherwise cause. */
    margin-bottom: -0.2em;
  }
}
```

`padding-bottom: 0.2em` pushes the bottom of the element's box down by 0.2em below the baseline. The background now extends into that space, which means the descenders are inside the clip region and render correctly.

`margin-bottom: -0.2em` cancels the same distance from the element's layout footprint. Without it, every gradient text element would push the next line down by an extra 0.2em, ruining vertical rhythm.

The two properties together: the box is visually extended to cover the descenders, but the surrounding layout is completely unaffected.

## Why 0.2em and not a pixel value

The `em` unit scales with `font-size`. This matters because `font-size` is fluid on this site: `clamp(1.35rem, 5vw, 1.5rem)` for body text, `clamp(2rem, 5vw, 4rem)` for headings. A fixed pixel value that clears the descenders at 2rem would under-clear them at 4rem and over-clear them at 1.35rem.

0.2em is approximately 0.22 UPM expressed in ems, which matches IBM Plex Sans's descender depth with a small buffer. It holds across every point in the fluid scale.

If you are adapting this to a different font, find the descender depth in the font's metrics. Most variable font inspection tools (Wakamai Fondue, FontDrop) surface this as "descender" in the font's `OS/2` table, expressed in UPM. Divide by the UPM value to get the em equivalent, then round up slightly for safety.

For IBM Plex Sans: descender is approximately -212 UPM out of 1000 UPM total, which gives 0.212em. Rounded up to 0.22em, then to 0.2em for a round number with a small buffer.

## The @supports guard

The full implementation wraps everything in `@supports (background-clip: text)`:

```css
.gradient-text {
  /* Fallback: solid text color, readable on any background */
  color: var(--color-text);

  @supports (background-clip: text) {
    display: inline-block;
    color: transparent;
    background-image: linear-gradient(135deg, var(--color-text), var(--color-accent));
    background-clip: text;
    padding-bottom: 0.2em;
    margin-bottom: -0.2em;
  }
}
```

Without the guard, a browser that does not support `background-clip: text` renders `color: transparent` on visible text. The fallback makes the text fully readable in that case: solid `var(--color-text)` on the background color. The gradient is a progressive enhancement.

`background-clip: text` is [Baseline 2022](https://caniuse.com/background-clip-text), which means every major browser has supported it for at least two and a half years. The guard is still worth keeping: it costs nothing and ensures graceful degradation in any edge case.

## Edge case: multiline gradient text

The `padding-bottom` fix only covers the last line of a multiline gradient text element. If the text wraps to multiple lines, intermediate lines do not need the fix (the next line's ink sits above the box bottom), but the last line does.

In practice, multiline gradient text is usually a heading where `text-wrap: balance` is already applied to minimize wrapping. Keep headings to one line where possible. If wrapping is unavoidable, the fix still works: `padding-bottom` extends the box on the last line, which is where the clipping would occur.

## Edge case: gradient direction and the baseline

The descender fix is independent of the gradient direction. Whether the gradient runs horizontally, vertically, or diagonally, the clipping happens at the box boundary, not along the gradient direction. Changing the `linear-gradient` angle does not affect whether descenders are clipped.
